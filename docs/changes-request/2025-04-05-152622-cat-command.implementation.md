# USM Cat Command - Implementation Documentation

## Overview

The USM Cat Command provides users with the ability to display aggregated user story content from change request files. This feature allows users to quickly view the full context of a change request in one place without manually opening multiple files.

The implementation satisfies two key user stories:
1. Display aggregated user story content from a change request (`usm cat`)
2. Exclude content-hash from `usm cat` output by default

This document describes the technical implementation, architecture decisions, and key components developed across four phases: foundation, minimum viable implementation (MVI), functionality extensions, and refinement.

## Architecture and Design

### Command Structure

The implementation follows the Cobra command pattern used throughout the USM CLI, with a clear separation of concerns:

* **Command Definition**: The `catCmd` variable in `cmd/cat.go` defines the command interface using the Cobra framework, including flags, arguments, and help text.
* **Command Options**: The `CatOptions` struct encapsulates all parameters that affect the command's behavior, facilitating clean passing of configuration.
* **Output Interface**: The `UserStoryOutput` interface decouples the command logic from terminal implementations, enhancing testability and flexibility.
* **Processing Results**: The `ProcessingResult` struct tracks operation statistics for generating informative summaries.

### Key Algorithms

#### User Story Content Processing

The core processing logic in `processAndPrintUserStories` follows these steps:

1. Compile the filter regex pattern (if provided)
2. Initialize processing statistics tracking
3. For each user story in the change request:
   a. Check if the story should be excluded
   b. Print the file path as a markdown comment
   c. Check if the user story file exists
   d. Read and process the user story content
   e. Apply filtering based on pattern (if any)
   f. Apply content formatting based on output mode
   g. Print the processed content
   h. Add a separator between stories
4. Display a summary of processing results if appropriate

#### Content Hash Filtering

The `FilterContentHash` function in `internal/utils/content_filter.go` is responsible for selectively removing content hash lines:

1. If `includeContentHash` is true, return the original content unchanged
2. Split content into lines and process line by line
3. Track metadata section boundaries using `---` markers
4. Only remove `_content_hash:` lines from the first metadata section
5. Preserve any content hash entries in subsequent metadata sections
6. Join lines back together preserving original formatting

#### Compact Output Formatting

The `createCompactOutput` function in `cmd/cat.go` extracts and formats user stories in a compact representation:

1. Extract the title from content using regex
2. Parse the content to identify the "As ... I want ... so that ..." pattern
3. Handle both single-line and multi-line user story formats
4. If a single-line format is detected, split it into multiple lines
5. Return a properly formatted multi-line user story with title

## Data Structures

### CatOptions

The `CatOptions` struct centralizes all parameters affecting command behavior:

```go
type CatOptions struct {
    ShowContentHash   bool     // Whether to include content hash in output
    ChangeRequestPath string   // Path to change request file
    FilterPattern     string   // Regular expression to filter stories by title or content
    ColorOutput       bool     // Whether to use colorized output
    CompactMode       bool     // Whether to use compact output format
    ExcludeStories    []string // Stories to exclude (by title or path)
}
```

### UserStoryOutput

The `UserStoryOutput` interface decouples command logic from terminal implementations:

```go
type UserStoryOutput interface {
    Print(message string)
    PrintError(message string)
    PrintSuccess(message string)
    PrintWarning(message string)
    IsDebugEnabled() bool
}
```

### ProcessingResult

The `ProcessingResult` struct tracks operation statistics for generating summaries:

```go
type ProcessingResult struct {
    TotalStories     int
    DisplayedStories int
    SkippedStories   int
    ErrorStories     int
}
```

## Key Architecture Decisions

### Content Hash Filtering Strategy

**Decision**: Filter content hash only in the first metadata section rather than all sections.

**Rationale**: This preserves user-added metadata in subsequent sections while still hiding implementation details in the primary section. This approach better handles complex markdown documents with multiple metadata blocks.

### Output Interface Abstraction

**Decision**: Introduce a `UserStoryOutput` interface instead of directly using terminal output.

**Rationale**: This abstraction decouples command logic from presentation concerns, making the code more testable and flexible. It allows for different output formats in the future without changing the core logic.

### Command Options Centralization

**Decision**: Encapsulate all command options in a dedicated `CatOptions` struct.

**Rationale**: Centralizing options improves code clarity and maintainability. It also simplifies parameter passing between functions and makes extending the command with new options easier.

### Processing Results Tracking

**Decision**: Add a dedicated `ProcessingResult` struct for tracking operation statistics.

**Rationale**: This approach simplifies summary generation and provides better context for understanding command execution outcomes. It helps users understand what happened during command execution, especially with large change requests.

## Testing Strategy

The command implementation is thoroughly tested with a comprehensive suite of unit tests:

1. **Mock File System**: Tests use a mock file system to avoid dependencies on actual files
2. **Test Coverage**: All key functions have high test coverage (90-100% for most functions)
3. **Edge Cases**: Tests cover error conditions, empty change requests, and malformed content
4. **Output Verification**: Tests verify both content and formatting of command output

## Usage Examples

The command supports several usage patterns:

```
# Basic usage - display all user stories in a change request
usm cat docs/changes-request/my-feature.md

# Display user stories with content hash included
usm cat docs/changes-request/my-feature.md --show-content-hash

# Filter user stories by pattern
usm cat docs/changes-request/my-feature.md --filter "auth|login"

# Show compact output format (title and "As ... I want ... so that ..." only)
usm cat docs/changes-request/my-feature.md --compact

# Exclude specific user stories
usm cat docs/changes-request/my-feature.md --exclude "auth,registration"

# Show colorized output
usm cat docs/changes-request/my-feature.md --color
```
